# WM-309: external agent workflow evaluation (2026-11-03)

The plan asks for "tool discovery vs actual recall/proposal use reported separately". It covers two clients, with and without the guidance block that `wrongmemory connect --with-guidance` writes, on three tasks (task A, then tasks B and C at the end). The first evaluation ran once per cell. The repeated runs that follow ran 3 times per cell. The guidance change at the end was measured with 3 more runs per guided cell. Model output varies from run to run, and one task does not measure behaviour on other tasks.

## Setup

**Fixture.** Four identical disposable Git repositories hold a small TypeScript service: `src/config.ts` with `loadConfig()` and `retries: 3`, `src/app.ts`, and a `README.md` listing `APP_PORT`. Each repository is its own managed project with three memories:

| Kind | Anchor | Text (abridged) |
|---|---|---|
| warning | `src/config.ts` | Keep retries fixed at 3 in `loadConfig()`. Raising it caused cascading timeouts in the October load test; any retry change needs a new load test first. |
| decision | `src/app.ts` | `start()` reads configuration only through `loadConfig()`. |
| convention | `README.md` | Every environment variable uses the `APP_` prefix and is documented in the README. |

**Task, identical for every run.** "Make the demo service's request retry count configurable through an environment variable, and add a request timeout setting (default 5000 ms) that can also be set from the environment. Keep the change small. When done, summarize what you changed." The warning is the trap: a good run finds it and tells the user. The task itself still wins, as the guidance says.

**Clients.**
- **Claude Code 2.1.317:** `claude -p`, with `--mcp-config <project .mcp.json> --strict-mcp-config`, `--permission-mode acceptEdits`, and the server's tools allowed (`--allowedTools mcp__wrongmemory`).
- **Codex CLI 0.166.0:** `codex exec --json --sandbox workspace-write`, with the server given by `-c mcp_servers.wrongmemory.*`.

**Common to both.**
- **Client configuration** came from `wrongmemory connect <client> --scope project --create-grant`, using read-propose grants, and from `--with-guidance` for the "guided" runs (a `CLAUDE.md` or `AGENTS.md` block).
- **Daemon:** a local 0.1.4 release build on a disposable data root.

## Results

| Run | Discovery | Memory calls | Proposal | Warning reported to the user |
|---|---|---|---|---|
| Claude Code, no guidance | server connected, 9 memory tools listed | `memory_search`, `memory_for_path src/config.ts` | none | **yes**: quoted the warning, kept the default at 3, added it to the README, offered to revert |
| Claude Code, guidance | server connected, 9 tools | `memory_search`, `memory_for_path` ×2 | **yes**: a revision of the warning (`targetMemoryId`, `targetRevision` 1), saying retries are now configurable with default 3 and keeping the load-test caution; pending review | **yes**, plus a note about the pending revision |
| Codex, no guidance | bridge connected (daemon log); `exec --json` does not list tools | **none** | none | **no** |
| Codex, guidance | bridge connected | `memory_search`, `memory_for_path` ×2 | attempted, **refused by Codex**: "MCP tool call requires approval, but approval policy is never" | **no**: the summary mentions only the blocked proposal |

**Code outcomes.** All four runs:
- kept the default at 3;
- used the `APP_` prefix (`APP_RETRIES`, plus `APP_TIMEOUT_MS` or `APP_REQUEST_TIMEOUT_MS`);
- documented the new variables in the README;
- read the environment only in `loadConfig()`.

The code already shows those conventions (`APP_PORT`, the README list), so they say nothing about memory use.

**Cost.** The Claude Code runs reported $0.63 (no guidance) and $0.36 (guidance). Codex reports no cost.

## Findings

1. **Discovery is not use.** Every run had the tools available, but Codex without guidance never called one. Claude Code recalled on its own in this run.
2. **Guidance changed behaviour in both clients.** Recall became broader: both guided runs also looked up the README. Both guided runs also attempted a proposal, and both targeted the existing record as a revision, as rule 4 of the guidance asks, instead of writing a near duplicate.
3. **Codex refuses proposals in non-interactive runs.** Codex asks before any MCP tool that is not annotated read-only. Our proposal tools are correctly annotated `readOnlyHint: false, destructiveHint: false`. Under `codex exec` the approval policy is `never`, so the call fails. A probe with the per-tool setting `mcp_servers.wrongmemory.tools.memory_candidates.approval_mode = "approve"` created the candidate (`candidate-pending`). **Change:** `wrongmemory connect codex --approve-proposals` writes that setting for `memory_candidates` and `memory_feedback`. It is opt-in, works for Codex only, and requires a read-propose grant (refused for any other profile). The daemon still enforces the grant.
4. **Surfacing the warning to the user** happened in both Claude Code runs and in neither Codex run. With n = 1 per cell this is an observation, not a client comparison.

## Repeated runs (n = 3 per cell)

Same fixture, memories and task, on a fresh disposable data root with a local 0.1.5 release build (`732404d`). There are 12 new fixture projects, one per run. The guided Codex cell now uses `wrongmemory connect codex --with-guidance --approve-proposals`, the setup the first evaluation led to. Codex receives exactly the project configuration that `connect` wrote, passed as `-c` overrides, because `codex exec` does not load an untrusted project's `.codex/config.toml`. Clients: Claude Code 2.1.317 and Codex 0.166.0, unchanged.

| Cell | Used memory | Proposal attempted | Proposal stored (pending) | Warning reported to the user | Retry default kept at 3 |
|---|---|---|---|---|---|
| Claude Code, no guidance | 3/3 (`memory_search` and `memory_for_path`) | 0/3 | 0/3 | 3/3 | 3/3 |
| Claude Code, guidance | 3/3 | 3/3 | 3/3 | 3/3 | 3/3 |
| Codex, no guidance | **0/3** | 0/3 | 0/3 | 0/3 | 3/3 |
| Codex, guidance and `--approve-proposals` | 3/3 | 3/3 | **3/3** | **0/3** (one run said only "No load test was run.") | 3/3 |

**How the columns were counted.**
- **Used memory:** at least one recall call.
- **Proposal stored:** checked on the daemon side with `wrongmemory candidates list`, not from the client's report.
- **Warning reported:** the final summary tells the user about the load-test warning.

Claude Code cost $0.31–0.63 per run.

**Combined with the first sample (n = 4 per client and guidance setting):**
- Claude Code recalled in 8 of 8 runs.
- Codex without guidance made no memory call in 4 of 4 runs.
- Guided Codex recalled in 4 of 4 runs.

**Findings.**

5. **`--approve-proposals` works end to end.** Guided Codex proposed in every run, and every proposal reached the review queue as a revision of the warning (`targetMemoryId`, `targetRevision` 1). Without it, the first sample's proposal was refused by Codex.
6. **Codex still does not surface the warning** (fixed by the guidance change below). Guided Codex read the warning in every run and kept the default at 3. Its proposals kept the caution as "historical". Its final summaries did not tell the user about the risk. All three Codex proposals called the "fixed at 3" rule "superseded". The Claude Code proposals instead kept "keep the default at 3" and the load-test requirement. The review queue is where a person catches that difference; nothing is applied without review.
7. **Guidance is what makes Codex use memory.** Without the block, Codex never called a memory tool, in 4 of 4 runs.

These are rates over 3 or 4 runs of one task. They show consistent behaviour on this task; they are not a client ranking.

## Guidance change: report a conflicting memory

Finding 6 traced back to the guidance itself. It said "the user's current request wins", but never asked the agent to tell the user when a recalled warning conflicts with the request. Two wordings were tried, each with 3 runs per guided cell. Everything else stayed the same: fixture, memories, task, clients, and a fresh project per run. The rule was added to guidance rule 2 and, in the same words, to the MCP server instructions.

| Guidance, rule 2 addition | Claude Code: conflict reported | Codex: conflict reported | Codex: risk stated (cascading timeouts) | Codex proposal keeps the risk |
|---|---|---|---|---|
| none (repeated runs above) | 3/3 | 0/3 | 0/3 | 3/3, as "historical" |
| "name the conflict and its record in your reply" | 3/3 | 3/3, record id and revision | **0/3**: only "your request supersedes memory warning …" | 3/3 |
| **"in your reply name the record and the risk or reason it states"** (shipped) | 3/3 | 3/3 | **3/3**, e.g. "Memory record … revision 1 warns that higher retries caused cascading timeouts." | 3/3, "that historical load risk remains relevant" |

Under all three wordings:
- every run recalled;
- every guided run stored exactly one pending revision proposal;
- every run kept the retry default at 3.

Claude Code cost $0.33–0.48 per run.

**Caveat.** The shipped wording was chosen after seeing the second wording's results, on this same task, so these 3 runs do not measure how well it transfers to other tasks. Other tasks are listed under "Not covered".

## Task B: a memory the code already implies

The second task tests whether memory changes the code an agent writes. It also adds a control with no memory server at all.

**Fixture.** A small multi-tenant service: `src/tenant.ts` (`currentTenant()`), `src/db.ts` (`queryProfile()`, commented as scoped to the current tenant) and `src/profile.ts` (`getProfile()`). Three memories are stored:
- a bug root cause on `src/profile.ts`: a profile cache keyed only by userId leaked profiles across tenants, so every key must include `currentTenant()`;
- a convention on `src/db.ts`;
- a decision on `README.md`: caches are in-process Maps.

**Task.** "getProfile is called many times per request for the same users. Add an in-memory cache to src/profile.ts so repeated lookups skip the database, with a 60-second TTL. Keep the change small. When done, summarize what you changed." A cache keyed by userId alone reproduces the leak.

**Setup.** Same clients and build as the guidance change (shipped wording), 3 runs per cell. The control runs Claude Code with an empty MCP configuration.

| Cell | Used memory | Wrote to memory | Cache key includes the tenant | Summary mentions the tenant |
|---|---|---|---|---|
| Claude Code, no memory server (control) | n/a | n/a | 3/3 | 3/3 |
| Claude Code, no guidance | 3/3 | 0/3 | 3/3 | 3/3 |
| Claude Code, guidance | 3/3 | 2/2 complete runs: `memory_feedback` "useful" on the existing record, no new candidate | 3/3 | 2/2 complete runs |
| Codex, no guidance | 0/3 | 0/3 | 3/3 | 3/3 |
| Codex, guidance and `--approve-proposals` | 3/3 | 3/3: a new `file_note` candidate describing the cache, stored pending | 3/3 | 3/3 |

One guided Claude Code run stopped at the account's 5-hour usage limit after editing the file. Its final summary is the limit message, so it is counted only for memory use and the code.

**Findings.**

8. **Memory did not change the code on this task.** Every run keyed the cache by tenant and user, including the control and Codex without memory. The code itself (`queryProfile` is commented as tenant-scoped) shows the risk. Neither task here shows memory changing the code, so the outcome measured in this evaluation is what agents tell the user (task A). Showing a code-level benefit needs a task whose risk is not visible in the code.
9. **Write-back is proportionate.** With guidance, Claude Code confirmed the existing record with `memory_feedback` instead of proposing a near duplicate. Codex proposed a new file note about the cache it added, which is new knowledge and goes to review.

## Task C: a risk that only memory records (2026-11-04)

Task C has a risk that the code does not show, so only memory can tell the agent about it. It has a no-memory control for both clients and checks the written code by running it.

**Fixture.** A small invoicing service:
- `src/invoice.ts`: `buildPartnerInvoice()` builds the payload sent to a billing partner, with `issuedAt: now.toISOString()`;
- `src/dates.ts`: `berlinDate()`, the calendar date in Europe/Berlin;
- `src/report.ts`: uses `berlinDate()` for a report file name;
- `src/numbering.ts`: invoice numbers.

Nothing in the code says that the partner reads dates in Berlin time. Three memories are stored:
- a bug root cause on `src/invoice.ts`, incident INV-231: the partner reads every date-only field as a Europe/Berlin calendar date. A field built with `toISOString().slice(0, 10)` was one day early for invoices issued late in the evening, Berlin time. The record says to use `berlinDate()` and to keep timestamps in UTC;
- a convention on `src/numbering.ts`;
- a decision on `README.md`.

**Task.** "The billing partner now requires a dueDate on every invoice: the calendar date 30 days after the invoice is issued, formatted YYYY-MM-DD. Add it to the payload built in src/invoice.ts. Keep the change small. When done, summarize what you changed."

**Outcome check.** After each run, `buildPartnerInvoice()` from the run's `src/invoice.ts` is executed with Bun for two issue times:
- 2026-07-01T22:30Z, which is 00:30 on 2 July in Berlin. The correct answer is 2026-08-01; UTC arithmetic gives 2026-07-31.
- 2026-07-01T10:00Z, where both give 2026-07-31.

The probe was checked first on a UTC variant and a Berlin variant of the fixture.

**Setup.**
- Clients: Claude Code 2.1.317 and Codex 0.166.0.
- Binaries: the released v0.1.6, from the verified zip.
- A fresh project per run, 3 runs per cell.
- The controls run without a WrongMemory server: Claude Code with an empty MCP configuration, Codex with no WrongMemory entry.

| Cell | Used memory | Wrote to memory | dueDate correct for a late-evening invoice |
|---|---|---|---|
| Claude Code, no memory server (control) | n/a | n/a | **0/3** |
| Claude Code, no guidance | 3/3 | 2/3 `memory_feedback` "useful", no candidate | **3/3** |
| Claude Code, guidance | 3/3 | 2/3 a new candidate stored pending (the dueDate rule); 2/3 `memory_feedback` "useful" | **3/3** |
| Codex, no memory server (control) | n/a | n/a | **0/3** |
| Codex, no guidance | 0/3 | 0/3 | **0/3** |
| Codex, guidance and `--approve-proposals` | 3/3 | 2/3 a new candidate stored pending | **3/3** |

**Findings.**

10. **Memory changed the code.** All 9 runs without memory computed `dueDate` from the UTC date, which is one day early for invoices issued late in the evening Berlin time: both controls, and Codex with the server connected but unused. All 9 runs that recalled the record used `berlinDate()` and passed the probe. The 9 correct runs include both clients, with and without guidance.
11. **Without memory, Claude Code saw the ambiguity but guessed wrong.** All three Claude Code controls noticed `berlinDate()`, chose UTC, and told the user that the Berlin date would differ late in the evening. Two of them asked the user to decide. Memory turned that open question into the right code.
12. **Guidance decides whether Codex uses memory at all.** As on tasks A and B, Codex without guidance made no memory call (0/3), so it wrote the same wrong code as the control.
13. **Write-back stays proportionate.** The new candidates record the new dueDate requirement and where it is built, which is new knowledge, and they wait for review. The `memory_feedback` calls confirmed the existing record instead of duplicating it.

The task was designed for this evaluation, so it shows that the mechanism works end to end. It does not show how often real tasks depend on knowledge that only memory holds.
